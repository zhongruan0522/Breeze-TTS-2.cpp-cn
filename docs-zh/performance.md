# 性能与调优

这里介绍运行速度、最近有哪些变化，以及哪些设置值得调整。

这里的每个数字都是在一张解锁了张量核心限制的 RTX 3060 12 GB 上测得的，除特别说明外均使用 Vulkan。[RTX 3080](#rtx-3080) 部分则是一张未做任何改动的原装卡。速度指的是实时率：每秒墙钟时间能生成多少秒音频，所以任何高于 `1.00x` 的值都比播放更快。重复运行会有几个百分点的波动，其他占用 GPU 的程序会带来更大偏差，所以在根据这些表格为你的配置做规划之前，请先在自己的卡上实测。[测量方法](#measuring)一节说明了如何测。

## v0.1.6 的新变化

- **声码器只解码新帧。** 以前每次 flush 都会重新解码约 88 帧旧音频然后把输出丢弃。现在它会在 flush 之间保留状态，因此一次 flush 只处理新工作。在默认块大小下，这把它从每帧约 6.6 ms 降到约 2.4 ms。对于 1 到 8 帧的小块，则从 14.95 ms 降到 2.74 ms。
- **首段音频快了约一倍。** 在预热完成的服务器上、Q4_K 量化下，从 181 ms 降到约 80 ms，因为第一个块现在可以是 1 帧，而不会拖慢剪辑的其余部分。
- **第一个块会自行调整大小。** `--chunk-first` 现在默认值为 1，并作为下限起作用。当 GPU 太忙、1 帧无法领先于播放时，第一个块会自动上调到 2、4 或 8 帧。
- **同时运行多个流。** `--parallel N` 让一台服务器最多同时生成 N 路流。它们共享每帧的一个 GPU 批次，因此三路流的代价远低于单路流的三倍。带引导和不带引导的流可以一起运行。
- **WebSocket 会等待空闲槽位。** 只有当所有槽位都被占用时，会话才会报告 `queued`，而且它在发声期间不再独占整个 GPU。

单路 Vulkan 流，v0.1.5 与 v0.1.6 背靠背对比，取 4 个种子的平均值。全部增益都来自声码器，骨干网络和深度解码器没有改动：

| 模型 | `cfg_scale` | v0.1.5 | v0.1.6 |
| --- | --- | --- | --- |
| Q4_K | 1 | 2.15x | 2.41x |
| Q4_K | 3 | 1.53x | 1.74x |
| Q8_0 | 1 | 1.78x | 1.99x |
| Q8_0 | 3 | 1.46x | 1.58x |

## 简要结论

1. **不要动 `--chunk-first` 和 `--chunk-max`。** 现在的默认值就是此处测得的最优数字。调高 `--chunk-max` 不再有任何好处。
2. **如果需要多于一路流，使用 `--parallel`。** 在 12 GB RTX 3060 上配合 Q8_0 或 Q4_K，`--parallel 3` 是安全设置。
3. **除非需要引导，否则保持 `cfg_scale` 为 1。** 它会损失约 25% 的速度，而且使用它的流要占两个槽位。
4. **如果速度不够，选更小的模型。** 深度解码器占每帧耗时的约三分之二，所以它的权重类型比其他任何因素都重要。
5. **保持预热开启。** 它在启动时多花几秒钟，却能在用户正在等待的请求上省下同样的时间。
6. **不要以首次运行的结果为准。** 见[首次运行更慢](#the-first-run-is-slower)。
7. **显存不够？** `--te-cpu` 能省约 1 GB，但不能与 `--parallel` 同时使用。见[显存不足](#short-on-video-memory)。

### RTX 3080

同一构建在一台原装 RTX 3080 12 GB 上、未解锁张量核心、使用 Vulkan。取 4 个种子的中位数，首段音频来自预热后运行一次的 `breeze-cli`：

| 模型 | `cfg_scale` 1 | `cfg_scale` 3 | 首段音频 |
| --- | --- | --- | --- |
| Q4_K | 3.50x | 2.81x | 约 140 ms |
| Q6_K | 3.67x | 2.87x | 约 130 ms |
| Q8_0 搭配 Q4_K 深度解码器 | 3.72x | 2.83x | 约 80 ms |
| Q8_0 | 3.16x | 2.71x | 约 145 ms |
| F16 | 2.71x | 2.32x | 约 140 ms |

在 Q8_0 下每帧为 5.7 ms 骨干网络、17.9 ms 深度解码器和 1.8 ms 声码器。3080 的显存带宽约为 3060 的 2.5 倍，所以权重类型的影响小得多：Q8_0 只比 Q4_K 慢约 10%，Q6_K 与 Q4_K 一样快，而 F16 比 Q4_K 在 3060 上的表现还要快。约每四次运行中有一次会出现一次较慢的声码器 flush，原因是 GPU 上有其他程序，这也是这里采用中位数的原因。

对深度解码器做量化是单项最大的速度收益，而且在多路流下依然成立，但它会损伤音频的高频部分，且损伤会随长文本不断累积。请先试听，相关数字在 [models.md](models.md) 中。各阶段的数字以及 CUDA 的对比见 [build.md](build.md#vulkan-or-cuda)。

## 运行多路流

```
breeze-server breeze-tts-2-q8_0.gguf --parallel 3
```

`--parallel N` 设置服务器拥有的槽位数，默认为 1。一路流占一个槽位，若其 `cfg_scale` 大于或小于 1 则占两个，因为引导会为每一帧生成两个版本。在 `--parallel 1` 下，使用引导的流仍然放得下。

以下全部是流之间相隔 1 秒启动、客户端从第一个数据包就开始播放且不做任何缓冲的情况：

| 流数 | 模型 | 后端 | 每路流速度 | 空隙 |
| --- | --- | --- | --- | --- |
| 1 | Q8_0 | Vulkan | 1.86x 到 2.15x | 无 |
| 1（带引导） | Q8_0 | Vulkan | 1.59x | 无 |
| 3 | Q8_0 | Vulkan | 1.24x 到 1.32x | 无 |
| 4 | Q8_0 | Vulkan | 1.08x 到 1.20x | 无，或最多 224 ms |
| 3 | Q8_0 搭配 Q4_K 深度解码器 | Vulkan | 1.42x 到 1.51x | 无 |
| 4 | Q8_0 搭配 Q4_K 深度解码器 | Vulkan | 1.18x 到 1.32x | 无 |
| 3 | Q4_K | CUDA | 1.38x 到 1.52x | 无 |
| 2 | F16 | Vulkan | 1.26x 到 1.29x | 无 |
| 1（带引导）+ 1（不带） | Q8_0 | Vulkan | 1.23x 到 1.36x | 无 |
| 1（带引导）+ 2（不带） | Q8_0 | Vulkan | 1.15x 到 1.28x | 无 |
| 1（带引导）+ 2（不带） | Q4_K | Vulkan | 1.09x 到 1.18x | 无 |
| 2（带引导） | Q8_0 | Vulkan | 1.16x 到 1.19x | 无 |
| 3（带引导） | Q8_0 | Vulkan | 0.87x 到 0.95x | **约 3 s，跟不上播放** |

三路带引导的流需要 6 个槽位，所以这里推荐的设置会拒绝这种负载，而不是任由它卡顿。

**在 12 GB RTX 3060 上应设置多少槽位：**

| 模型 | `--parallel` | 说明 |
| --- | --- | --- |
| Q8_0 或 Q4_K | `3` | 不带引导时余量充足。 |
| Q8_0 或 Q4_K | `4` | 可行，也能容纳 2 路带引导的流。速度已接近 1x，其他 GPU 负载可能造成空隙。 |
| Q8_0 搭配 Q4_K 深度解码器 | `4` | 每路流仍能达到 1.18x 或更好。 |
| F16 | `2` | |

### RTX 3080 上的多路流

原装 RTX 3080 在 `--parallel 6` 下，条件相同：流之间相隔 1 秒，客户端从第一个数据包开始播放且不做缓冲，每段约 15 到 20 s 音频：

| 流数 | Q4_K | Q8_0 搭配 Q4_K 深度解码器 | Q8_0 | F16 |
| --- | --- | --- | --- | --- |
| 3 | 2.30x 到 2.39x | 1.93x 到 2.12x | 1.84x 到 1.92x | 1.95x 到 2.14x |
| 4 | 1.94x 到 2.13x | 1.92x 到 2.08x | 1.59x 到 1.70x | 1.60x 到 1.69x |
| 5 | 1.70x 到 1.91x | 1.69x 到 1.93x | 1.46x 到 1.68x | 1.47x 到 1.61x |
| 1（带引导）+ 2（不带） | 1.95x 到 2.29x | 1.81x 到 1.95x | 1.75x 到 1.88x | 1.67x 到 1.72x |
| 2（带引导） | 1.82x 到 1.85x | 1.89x 到 1.97x | 1.78x | 1.70x 到 1.71x |
| 3（带引导） | 1.46x 到 1.69x | 1.49x 到 1.58x | 1.42x 到 1.51x | 1.24x 到 1.28x |

除 Q8_0 搭配 Q4_K 深度解码器在 5 路流时出现一次 18 ms 的空隙外，以上都没有空隙。在 3060 上跟不上播放的三路带引导的流，现在能跑到约 1.5x。所以在 3080 上，`--parallel 6` 对以上任何模型都是安全的，它能容纳 5 路不带引导的流，或 3 路带引导的流。

在其他卡上，从单路流的速度出发。批处理带来的收益超出直觉，因为各路流共享每一次权重读取：F16 跑一路流约 1.4x，两路流时每路约 1.3x。设定一个槽位数，同时发起同样多的请求，然后读服务器为每个请求打印的 `x` 数字。

**显存。** Q8_0 下三路流占用约 4.3 GB 显存，Q4_K 下约 3.2 GB。

**同时发起的请求。** 发起请求会在其提示处理期间暂停其他流，所以服务器会给快要耗尽音频的流最多 400 ms 让它先积累领先量。同时发起的请求仍然能干净地播放，但最后一个可能要等约 1 s 才拿到首段音频。混入引导时，请求突发是唯一需要客户端缓冲的情形：不缓冲的话会有最多约 1 s 的空隙。随附的 UI 已经缓冲了 1.25 s。

**槽位占满时。** HTTP 路由会立刻返回 `409`，而 WebSocket 会话会发送 `queued` 并等待。WebSocket 的每个片段各自占用槽位，所以各会话在片段之间轮流执行。声音转换会占满所有槽位，因此它需要服务器空闲，并在结束前阻止新流启动。注册声音在帧间隙运行，所以每路流都要等那次编码，约 650 ms。

**同一批次中相同种子会产生不同的音频。** 每路流有自己的随机数，但 GPU 舍入会随批次大小略有不同，这可能改变采样结果。语音质量一样好，只是不是同一次录制。如果需要完全可复现的输出，使用 `--parallel 1` 并逐个生成请求。

## 显存不足

`--te-cpu` 把文本编码器的权重放在系统内存里并在 CPU 上运行。骨干网络、深度解码器和声码器仍在 GPU 上。文本编码器只在任何音频输出之前读取文本，所以它是唯一可以移出 GPU 而不会拖慢流本身的部分。它面向 4 到 6 GB 的显卡，或与本地 LLM 之类共享显卡的场景。显存充裕的卡上请保持关闭。

`BREEZE_TE_THREADS` 设置它使用的 CPU 线程数，默认为你的核心数的一半。C API 和 Python 绑定没有对应的参数，改为在环境中设置 `BREEZE_TE_CPU=1`。

RTX 3060 上 Q8_0 的单路流、6 线程、一段拆成两个片段的文本。显存为模型实际占用，已排除其他程序：

| `cfg_scale` | 文本编码器 | 显存 | 两个片段的编码总时长 | 首段音频 |
| --- | --- | --- | --- | --- |
| 1 | GPU | 3.7 到 3.9 GB | 0.1 s | 0.3 到 0.4 s |
| 1 | CPU | 2.7 GB | 1.5 s | 0.5 s |
| 3 | GPU | 4.0 GB | 0.1 s | 0.3 s |
| 3 | CPU | 2.8 到 2.9 GB | 2.4 到 2.7 s | 0.8 到 1.0 s |

所以在 Q8_0 下约省 1 GB，Q4_K 下约省 0.9 GB。一旦音频开始输出，速度与不使用它时相同。代价是音频输出之前的时间：

- **每个片段都要付出这个代价。** 长文本会被拆成片段，见 [`--split-chars`](#--split-chars)，每个片段开始时都要编码。每片约 0.7 s，带引导时约 1.3 s，因为引导要对文本编码两次。第一个片段的耗时计入首段音频的等待；后续片段启动时，流通常已大幅领先于播放，所以这段停顿一般已被客户端已持有的音频覆盖。
- **相同种子的音频略有不同。** CPU 的舍入稍有差异，剪辑内容会变，但声音不变。

**不要与 `--parallel` 组合使用。** 服务器在同一条线程上编码文本并生成所有流，所以编码期间所有其他流都会停止。使用 `--te-cpu` 时，每个新请求和长文本的每个新片段都会让其他流停顿 0.7 到 1.3 s。共享 GPU 的流只比播放快约 1.1 到 1.3x，无法补回这段时间，你会听到空隙。这个组合未经过测量，所以如果必须同时使用，请先用自己的客户端测试。

## 调优设置

### `--chunk-max`

最大块，默认 25 帧（2 s）。这曾经是最主要的调优对象，因为每次 flush 都会丢弃固定的声码器工作量。这个开销已经消除，所以现在它只决定音频到达的频率。Q8_0 下的 18 秒剪辑：

| `--chunk-max` | flush 次数 | 每帧声码器耗时 |
| --- | --- | --- |
| 8 | 31 | 2.90 ms |
| 25 | 15 | 2.17 ms |
| 50 | 13 | 2.16 ms |

- **调高到 25 以上没有任何收益**，只会让客户端在块之间等更久。如果你在旧版本上设过 `--chunk-max 40`，把它去掉。
- **调低它代价很小。** 降到 8 只损失约 2% 的总速度，而客户端需要的缓冲大幅减少，因为等待一个块的最长时间从约 1 s 降到约 300 ms。

### `--chunk-first`

允许的第一个块的最小值，默认 1 帧（80 ms）。服务器根据当前负载下帧的实际耗时选择真实大小：

| 该负载下的近期速度 | 第一个块 |
| --- | --- |
| 1.9x 或更好 | 1 帧 |
| 1.5x 到 1.9x | 2 帧 |
| 1.15x 到 1.5x | 4 帧 |
| 低于 1.15x | 8 帧 |

只有当客户端无法处理很小的数据包时才调高它，因为这会推迟第一声。在 Q8_0 下的 `breeze-cli` 中，值为 4 时首段音频为 394 ms，默认值为 278 ms，而每帧只省了 0.14 ms。把两个参数设为同一个数字会关闭这个渐进机制，以固定大小流式输出。

### `cfg_scale`

引导对单路流损失约 25% 的速度。深度解码器在同一个计算图中运行一帧的两个版本，所以远不到两倍。2 和 3 的代价相同，只有 1 是免费的。

### `--split-chars`

这与长文本有关，与速度无关。一次性要求生成几分钟的文本时模型会丢失文本，所以长文本会被拆分，见 [cli.md](cli.md)。每个片段都会开始一个新提示，在 `--parallel` 下这会短暂暂停其他流，所以很小的值会让这些停顿更频繁。默认值为 600。

### `--no-warmup`

预热会遍历你的槽位数允许的每一种流组合，所以槽位越多耗时越长。Q8_0 下服务器就绪所需的时间：

| 设置 | 就绪耗时 |
| --- | --- |
| `--no-warmup` | 约 3 s |
| `--parallel 1` | 约 6 到 7 s |
| `--parallel 3` | 约 9 s |
| `--parallel 4` | 约 11 s |

开启预热时，启动后的第一个请求约 200 到 350 ms 到达首段音频，之后的请求约 80 ms。关闭预热时，第一个请求以及每种流组合首次出现时，都会在有人正在收听的时候构建 GPU 流水线。

### 客户端缓冲

单路流，或间隔启动的几路流，服务器现在会在客户端快耗尽时提前发送音频，上述测试在不做任何缓冲的情况下都没有空隙。缓冲仍然是对抗其他 GPU 负载和请求突发的最廉价手段。要渐进填充缓冲水位，而不是推迟开始播放，见[无卡顿流式播放](server.md#streaming-without-stutter)。

## 首次运行更慢

GPU 驱动在第一次遇到新的张量形状和类型时会编译一条新流水线，然后把它保存在磁盘缓存里。表现为一次性的停顿，而且可能很大：声码器在 Q4_K 和 F16 下的首次运行分别为每帧 44 ms 和 177 ms，第二次运行则是 2.28 ms 和 2.49 ms。更新 GPU 驱动会让缓存失效、重新出现。`breeze-server` 在预热阶段完成了大部分工作，但 `breeze-cli` 没有预热，所以跑两次，以第二次为准。

## 测量方法

`breeze-cli --timings` 按阶段打印一次请求：

```
time to first audio 190 ms over 9 flushes
  reference encode       0.0 ms
  prompt build          42.0 ms
  backbone prefill      39.5 ms
  first vocoder         45.9 ms  (1 frames)
  backbone decode      712.3 ms  (9.37 ms/frame)
  depth decode        1924.3 ms  (25.32 ms/frame)
  vocoder              279.0 ms  (3.67 ms/frame)
  76 frames, 6.08 s audio
```

实时率为 `80 / (骨干网络 + 深度解码器 + 声码器每帧耗时)`。像这样的短剪辑上每帧声码器耗时会显得偏高，因为一次 flush 有约 8.5 ms 的固定成本，而短剪辑的小 flush 更多。

`breeze-server --verbose` 在每次请求后打印相同的每帧数字，其上一行是该请求达到的速度，例如 `1.29x`。要在负载下看那个数字，因为每帧的阶段数字不包含等待其他流的时间。

如果某次运行比平时慢得多，先检查 GPU 上还有什么在跑，再重新运行一次，不要急着改设置。这里的失败案例——Q8_0 只有 1.53x、F16 只有 0.95x——在相同设置下重跑就恢复正常了，而且服务器空闲时这里测到过 46% 的 GPU 负载。

## 卡顿时排查

| 现象 | 可能原因 | 处理办法 |
| --- | --- | --- |
| 有空隙，速度低于 `1.00x` | GPU 跟不上 | 换更小的模型、关闭引导、调低 `--parallel`，或关闭其他占用 GPU 的程序 |
| 有空隙，速度远高于 `1.00x` | 客户端缓冲对该块大小来说太小 | 加大缓冲，或调低 `--chunk-max` |
| 仅在多路流运行时有空隙 | 对这张卡来说流太多 | 调低 `--parallel` 或换更小的模型 |
| 仅在请求同时发起时有空隙 | 上述突发情形 | 缓冲约 1 s，或把请求错开 |
| 第一个请求慢，之后正常 | 流水线正在构建 | 保持预热开启，见上文 |
| HTTP 路由返回 `409` | 所有槽位都被占用 | 调高 `--parallel`、稍后重试，或改用会等待的 WebSocket |
| 使用 `--te-cpu` 时，每当请求或新片段启动就出现空隙 | CPU 文本编码器暂停了其他流 | 只在 `--parallel 1` 下使用 `--te-cpu` |
| 某次运行比上一次慢得多 | GPU 上有其他程序 | 检查 GPU 负载并重新运行 |
